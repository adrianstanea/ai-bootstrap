# Graphviz Diagrams

This file decides **what** to draw and **how** to keep it consistent. Syntax and patterns live in `references/`. **Load only the reference you need for the current step.** Don't load all of them.

## Workflow

1. **Name the reader's question.** One diagram answers one question ("what depends on what?", "how does data move through the pipeline?").
2. **Confirm Graphviz is the right tool** ([Graphviz or something else](#graphviz-or-something-else)).
3. **Pick a pattern and an engine** from the [pattern table](#pattern-table). Load that pattern file.
4. **Load the core references on demand:**
   - `references/dot-language.md` for syntax, quoting, attribute scopes, subgraphs/clusters, and ports. Load it if you're unsure of any syntax.
   - `references/layout.md` when placement is wrong or must be controlled (ranks, ordering, edge routing, engine options).
   - `references/labels-html.md` for multi-line, aligned, or table-style labels (records, UML boxes, schemas).
   - `references/style-conventions.md` when creating the first diagram in a repo, adding a legend, or harmonising styles.
   - `references/embedding.md` for Sphinx/MyST/Doxygen integration, external files, output formats, and generated graphs.
5. **Write the diagram** following the [universal rules](#universal-rules).
6. **Validate:** `python scripts/check_dot.py <files>` (supports `.dot`, `.gv`, `.rst`, `.md`). Add `--render` to run `dot` if it's installed. Fix every `ERROR` and review each `WARN`.

## Graphviz or something else

| Situation                                                                                      | Use                                                                                     |
| ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| The doc builds with Sphinx/Doxygen, or graphs are generated by tools (CMake, Doxygen, scripts) | **Graphviz**                                                                            |
| Large or dense graphs, fine control over ranks, ports, record/table nodes                      | **Graphviz**                                                                            |
| The doc is plain GitHub/GitLab Markdown with no build step                                     | Mermaid (GitHub doesn't render DOT), or commit a rendered SVG next to the `.dot` source |
| Time-ordered interactions between participants                                                 | Sequence diagram (Mermaid/PlantUML). Graphviz has no lifelines                          |
| Gantt/timeline/charts                                                                          | Not Graphviz                                                                            |

## Pattern table

| Reader's question                                                          | Pattern file                    | Graph type                      | Engine                            | Direction                           |
| -------------------------------------------------------------------------- | ------------------------------- | ------------------------------- | --------------------------------- | ----------------------------------- |
| Which components/layers exist, and how do they connect?                    | `patterns/architecture.md`      | `digraph` + clusters            | `dot`                             | `TB` (layers) / `LR` (request path) |
| What depends on what (packages, CMake targets, modules, includes)?         | `patterns/dependency-graph.md`  | `digraph`                       | `dot`                             | `BT` or `TB`                        |
| How does data/work move through stages (pipelines, CI, DFDs)?              | `patterns/dataflow-pipeline.md` | `digraph`                       | `dot`                             | `LR`                                |
| Which states exist, and what triggers transitions?                         | `patterns/state-machine.md`     | `digraph`                       | `dot`                             | `LR`                                |
| What types exist, and how do they relate (UML-style classes)?              | `patterns/class-uml.md`         | `digraph` + HTML labels         | `dot`                             | `BT` (inheritance up)               |
| What is the data/config schema with keys and references?                   | `patterns/schema-er.md`         | `digraph` + HTML tables + ports | `dot`                             | `LR`                                |
| What is the hierarchy (dir tree, ownership, call tree, decision tree)?     | `patterns/tree-hierarchy.md`    | `digraph`                       | `dot` (`twopi` if radial)         | `TB`                                |
| How are peers/devices/services interconnected (no direction or hierarchy)? | `patterns/network-topology.md`  | `graph` (undirected)            | `neato`/`fdp` (`circo` for rings) | n/a                                 |

If two patterns fit, prefer the one whose **edges** mean what the reader cares about (dependency vs data movement vs control). If the material needs two views, draw two diagrams.

## Universal rules

**Scope**

- One question per diagram. Budget about **20 nodes / 30 edges**. Above that, split it into an overview plus detail diagrams, or collapse groups into single nodes.
- Give every diagram a caption (Sphinx `:caption:`) or a heading, plus one sentence explaining what to look for.

**Source structure.** Use this order in every file:

1. Header comment: purpose, owner/source of truth, and how to regenerate if it's generated.
2. Graph attributes (`rankdir`, `fontname`, `newrank`, `compound` …).
3. Default `node [...]` and `edge [...]` statements.
4. Node declarations, grouped by cluster/subgraph, each with its label.
5. Edges, grouped by meaning (main flow first, then secondary), with no attributes repeated per edge where a default or subgraph scope would do.

**Identifiers and labels**

- IDs are short, stable `snake_case` ASCII (`order_svc`). Labels are human text (`label="Order service"`). Never use the label as the ID. This keeps diffs and refactors cheap.
- Quote any ID or value that isn't a plain identifier or number. Quote and escape `"` as `\"`.
- Keywords (`node`, `edge`, `graph`, `digraph`, `subgraph`, `strict`) are case-insensitive. Quote them if they're used as IDs.
- Clusters **must** be named with the `cluster` prefix (`subgraph cluster_backend`), or they aren't drawn as boxes.

**Semantics over decoration**

- Give each shape, line style, and arrowhead one meaning, and use it the same way across the doc set (see `style-conventions.md`). Add a legend when you use more than one encoding.
- Edge direction must be consistent within a diagram. For example, in a dependency graph the arrow always points from dependant to dependency.
- Set `fontname` at graph, node, and edge level (the default Times font looks out of place in modern docs).

**Layout hygiene**

- Fix layout problems with structure first: declaration order, clusters, `rank=same`, `group`. Use `weight`, `constraint=false`, and `minlen` next. Use invisible nodes/edges last, and comment each one.
- Don't hard-code positions (`pos`, `pin`) for `dot`. It ignores them.

**Maintainability**

- Keep large diagrams in `.dot` files under `docs/diagrams/` (or the existing convention) and reference them with `.. graphviz:: path.dot`. Keep small ones (fewer than about 15 lines) inline.
- Don't hand-edit generated graphs. Regenerate them, then post-process with a script if needed (see `embedding.md`).

## Updating an existing diagram

1. Read the whole source first. Reuse its IDs, default node/edge styles, and conventions. Don't restyle unrelated parts.
2. Add new nodes in the matching cluster/section, and new edges in the matching edge group.
3. Remove nodes and edges for deleted components. Stale diagrams are worse than none.
4. Run `scripts/check_dot.py`, and if possible render and compare before and after.

## Reviewing a diagram

Report in this order: wrong pattern for the question, then syntax/render errors, then semantic inconsistencies (edge direction, shape meaning), then layout issues, then style. Propose corrected DOT, not just comments.
